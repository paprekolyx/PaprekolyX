## Правила работы со скриптами

1. **Идемпотентность.** Скрипт можно запускать повторно, и он не должен ничего
   ломать или дублировать. Для этого используются:
   - `create table if not exists`, `add column if not exists`;
   - `drop policy if exists` перед `create policy`;
   - `insert … where not exists (…)` вместо вставки «в лоб».
2. **Никаких разрушающих действий.** `drop table`, `drop column`, `truncate`
   и `delete` без `where` в скрипты не попадают. Если такое действительно нужно —
   отдельный файл с пометкой `DANGER` в названии и с резервной копией beforehand.
3. **Один скрипт — одна задача.** Не смешивать схему, данные и политики в одну кучу.
4. **Комментарий в шапке** каждого файла: что делает, зачем, безопасно ли.

## Принятые решения

**Промокоды закрыты для публичного чтения.**
В техпаспорте (§7) указано «promo_codes — SELECT всем», но при публичном чтении
любой посетитель увидит все действующие промокоды в консоли браузера.
Проверка кода будет делаться на стороне базы через функцию
(`security definer` RPC), которая возвращает только факт применения скидки.

**Старое поле `orders.status` (текст) сохранено.**
Рядом добавлено `orders.status_id` — связь со справочником. Текстовое поле
удалим отдельным скриптом, когда форма заказа полностью перейдёт на `status_id`.

**Таблица `cart_items` не создавалась.**
Корзина хранится в браузере (localStorage) — этого достаточно, пока нет
авторизации через ВК. Появится авторизация — появится и таблица.

## Функция `create_order` — как создаются заказы

Заказ создаётся не прямым `INSERT` с сайта, а вызовом серверной функции:

```js
const { data, error } = await db.rpc('create_order', { p: payload });
```

**Что делает функция одним атомарным действием:**

1. проверяет имя, наличие хотя бы одного способа связи, состав корзины;
2. берёт цены **из таблицы `products`**, игнорируя всё, что прислал браузер;
3. создаёт запись в `orders` со статусом `new`;
4. сохраняет позиции в `order_items` со снапшотом цен;
5. создаёт запись в `deliveries` (если выбран способ доставки);
6. делает первую запись в журнале `order_status_history`;
7. возвращает сайту только номер заказа и суммы.

**Ограничения:** не более 3 заказов за 10 минут с одного телефона / ВК / e-mail;
не более 50 позиций в заказе; заказать можно только товары с `is_active = true`.

**Почему так, а не прямой INSERT:**

| Прямой INSERT с сайта | Через функцию |
|---|---|
| Цену можно подменить в консоли браузера | Цену считает сервер |
| Заказ и позиции могут разойтись | Одна транзакция — всё или ничего |
| Нужно открыть `SELECT` на `orders`, чтобы узнать номер | Функция сама возвращает номер |
| Проверки живут в браузере, их легко обойти | Проверки на сервере |

После установки функции прямой `INSERT` в `orders` и `order_items` для роли `anon`
закрыт — единственной точкой записи остаётся функция.

## Таблица `site_content` — тексты сайта без правки кода

Всё, что может часто меняться, вынесено из HTML в базу: контакты, цены доставки,
слоганы, логотип и промо-картинка. Правится в **Table Editor → site_content**,
публикация сайта не требуется.

Связь с HTML через атрибуты:

| Атрибут | Что подставляет |
|---|---|
| `data-content="ключ"` | текст элемента |
| `data-content-src="ключ"` | адрес картинки |
| `data-content-href="ключ"` | адрес ссылки |

Текст внутри тега остаётся запасным: если база недоступна или ключ пуст,
посетитель видит значения из HTML.

> **Следите за парой `contacts.phone_display` и `contacts.phone_href`.**
> Сейчас показан номер `+7 (925) 052-19-XX`, а по клику набирается `+79250521900`.

## Ключи

В `index.html` лежит **публичный** ключ `sb_publishable_…` — так и должно быть.

**Секретный ключ (`sb_secret_…` / `service_role`) не должен попадать ни в один файл
репозитория.** Репозиторий публичный. Если секрет всё же закоммичен — его нужно
немедленно отозвать в Supabase → Project Settings → API Keys и выпустить новый:
удаление файла из истории не убирает.
