# План: смена статусов заказа из админ-панели

**Статус:** реализовано 18.09.2026 (скрипт `09_paid_flag_and_status_change.sql`, блок «Управление» в карточке заказа).
Ответы заказчика учтены: миграция paid выполняетcя по плану; отдельной метки предоплаты нет;
в журнале истории появилась роль; отмена оплаченного заказа запрещена до снятия флага.
**Связано:** `docs/plan-orders-viewer.md`, скрипты `06`, `08`.

---

## 1. Главное изменение модели: «оплачен» — это не статус

Сейчас `paid` живёт в справочнике `order_statuses` рядом с «Новый» и «Доставлен».
Это смешивает два разных измерения:

| Измерение | Вопрос | Где живёт |
|---|---|---|
| Этап работы | На какой стадии заказ (новый, в работе, отправлен)? | `orders.status_id` |
| Деньги | Оплачен ли заказ (полностью или предоплатой)? | новое поле `orders.is_paid` |

Заказ может быть «в работе» и одновременно оплачен предоплатой; может быть
«доставлен» и не оплачен целиком. Статусом это не выразить.

### Миграция

1. Добавить поля:
   - `orders.is_paid boolean not null default false`;
   - `orders.paid_at timestamptz null`.
2. Перенести данные: заказы со статусом `paid` получают `is_paid = true`
   и переходят в статус `confirmed` (деньги получены, работа ещё не начата);
   заказы со статусом `paid`, у которых есть история «в работе», получают `in_progress`.
3. Удалить код `paid` из `order_statuses` и переходы с ним из `status_transitions`.
4. Новая статусная модель после миграции:
   `new → confirmed → in_progress → ready → shipped → delivered`,
   отмены из `new / confirmed / in_progress`, возврат из `delivered`.

## 2. Серверная часть

Три функции `security definer`, каждая проверяет хеш пароля и пишет журнал:

| Функция | Что делает |
|---|---|
| `admin_set_status(hash, order_id, status_code, comment)` | Проверяет, что переход разрешён в `status_transitions`; меняет `status_id`; пишет строку в `order_status_history` с `changed_by = 'admin'` и комментарием |
| `admin_set_paid(hash, order_id, is_paid)` | Ставит `is_paid` и `paid_at`; при `true` создаёт строку в `payments` с `payment_type = 'full'` и суммой заказа; при снятии оплаты удаляет созданную ею строку |
| `admin_order_actions(hash, order_id)` | Возвращает для карточки: текущий статус, список разрешённых следующих статусов, значение `is_paid` |

Правила внутри `admin_set_status`:

- переход возможен только по `status_transitions`;
- в завершающие статусы (`delivered`, `cancelled`, `returned`) вход есть, выход — нет;
- повторная установка того же статуса отклоняется;
- каждый успешный вызов пишет историю, поэтому путь заказа восстановим.

Прямые `update orders` из браузера по-прежнему закрыты RLS.

## 3. Интерфейс кабинета

В карточке заказа появляется блок «Управление» (только в кабинете, на витрине ничего не меняется):

1. Текущий статус пилюлей того же вида, что в таблице и воронке.
2. Рядом — кнопки разрешённых следующих статусов (из `admin_order_actions`);
   нажатие открывает маленькое окно с полем комментария и подтверждением.
3. Тумблер «Оплачен» с датой оплаты; при включении просит подтвердить сумму.
4. Под блоком — история статусов с пометками, кто и когда менял (`admin` / `customer`).

Дополнительно в таблице заказов:

- колонка «Оплата» с меткой «оплачен / не оплачен» отдельно от статуса;
- фильтр-чип «Только неоплаченные».

В статистике:

- воронка статусов перестаёт содержать «Оплачен»;
- новый KPI «оплачено заказов» и доля оплаченных от всех;
- в CSV-сводку добавляются колонки `is_paid` и `paid_at`.

## 5. Риски и вопросы, которые нужно решить до разработки

1. **Что делать с заказами, которые сейчас в статусе `paid`?** План предполагает переход
   в `confirmed` + `is_paid = true`. Если у вас есть заказы, где после оплаты сразу
   началось изготовление, их нужно перевести в `in_progress` — это решается условием
   по истории статусов, но список стоит посмотреть глазами до миграции.
2. **Частичная оплата.** Предоплата 40% и доплата 60% — это две строки в `payments`,
   но один булев флаг «оплачен» означает «оплачено полностью». Нужна ли отдельная
   метка «предоплата получена»? Если да, добавляется поле `prepayment_paid`
   (оно уже есть в `custom_orders`, но не в `orders`).
3. **Кто видит кнопки смены статуса.** Кабинет один и пароль один, поэтому
   разграничения внутри кабинета не будет; журнал истории покажет, что менял `admin`.
4. **Отмена оплаченного заказа.** Нужен ли запрет отменять заказ с `is_paid = true`
   без снятия оплаты сначала? План предполагает запрет, чтобы не терять связь
   денег и статуса.
