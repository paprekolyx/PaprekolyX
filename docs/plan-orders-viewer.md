# План: страница просмотра заказов (`orders.html`)

**Статус:** реализовано 18.09.2026 с правками заказчика (см. ниже). Страница — `orders.html`,
SQL — `supabase/06_admin_orders.sql`.

## Правки заказчика, учтённые при реализации

| Было в плане | Стало |
|---|---|
| Счётчик оплаченных заказов | Убран: сайт не получает информацию об оплатах |
| Статусная модель не детализирована | Таблица `status_transitions`: 11 разрешённых переходов, отображается как Jira workflow |
| Один комментарий | Учтены оба: комментарий к заказу и комментарий к доставке |
| Загрузка не описана | Скелетон в стиле клиентской части сайта |
| Ограничения защиты только в плане | Продублированы в раскрывающемся блоке на странице и в техпаспорте (раздел 7.3) |
| Доступ с любых устройств | Только ПК: на телефоне красивый экран-заглушка |
| Контакты как есть | Маскируются звёздочками по умолчанию, кнопка «глазик» раскрывает |
| Выгрузка не планировалась | Кнопка «Выгрузить в CSV» (BOM, разделитель `;`) |
**Границы:** только просмотр. Изменение статусов, создание и удаление заказов — не входят.

---

## 1. Зачем и что получится

Отдельная страница сайта, на которой виден список всех заказов из базы:
кто заказал, что именно, на какую сумму, каким способом оплаты и доставки,
в каком статусе. Вход — по паролю. Страница не ссылается из общего меню,
попасть на неё можно только по прямому адресу:

```
https://paprekolyx.github.io/PaprekolyX/orders.html
```

Это учебный проект, поэтому защита сознательно простая. Ниже честно указано,
чего в ней нет и что добавило бы настоящую аутентификацию.

---

## 2. Главная проблема и её решение

Сейчас заказы **нельзя прочитать анонимно** — и это правильно: в них имена,
телефоны и e-mail клиентов. Значит, странице нужен способ получить данные,
не открывая их всему интернету.

Решение — **серверные функции с проверкой пароля внутри базы**:

| Функция | Что делает | Кто может вызвать |
|---|---|---|
| `admin_check_password(hash text)` | Возвращает `true`, если хеш совпал с сохранённым | anon |
| `admin_orders(hash text)` | Возвращает заказы JSON-ом, **только если хеш совпал**; иначе ошибка | anon |

Обе — `security definer`, то есть выполняются от имени владельца таблиц и сами
решают, отдать данные. Таблица заказов при этом остаётся закрытой для чтения:
обойти функцию и прочитать `orders` напрямую по-прежнему нельзя.

Пароль в базу **в открытом виде не кладём**. Храним его SHA-256 хеш.
Страница считает хеш от введённого текста через Web Crypto API
(`crypto.subtle.digest`) и отправляет на проверку только хеш.

## 3. Изменения в базе

### 3.1. Новая таблица — одна

```
admin_credentials
├── key           text      PK      'admin'
├── password_hash text      NN      SHA-256 от пароля, 64 hex-символа
├── created_at    timestamptz       now()
└── updated_at    timestamptz       триггер, как в site_content
```

RLS: **включён, политик на чтение нет вообще**. Даже хеш никто не прочитает
через PostgREST — сравнение происходит только внутри функций.

### 3.2. Служебная функция задания пароля

```
admin_set_password(new_password text)
```

Вызывается **один раз вручную из SQL Editor** (не со страницы). Считает хеш
и кладёт в таблицу. Повторный вызов меняет пароль. Из браузера её вызвать
нельзя: права только у роли, под которой выполняется SQL Editor.

### 3.3. Новые таблицы не нужны для самих заказов

Всё уже есть: `orders`, `order_items`, `products`, `product_images`,
`order_statuses`, `payment_methods`, `delivery_methods`, `deliveries`,
`order_status_history`. Кабинет только читает их через функцию.

### 3.4. Что возвращает `admin_orders`

Один вызов отдаёт всё нужное одним JSON-ом, чтобы страница не делала
десять запросов:

```
{
  orders: [
    {
      id, created_at, status_code, status_name,
      customer_name, customer_phone, customer_vk, customer_email,
      payment_name, delivery_name, delivery_point,
      total, delivery_cost, grand_total, comment,
      items: [ { article, name, quantity, price, image_url } ],
      history: [ { status_name, changed_at, changed_by } ]
    }
  ],
  stats: { total_orders, new_orders, revenue }
}
```

Сортировка — по дате создания, новые сверху. Ограничение — последние 200
заказов, чтобы ответ не рос бесконечно.

## 4. Интерфейсы

### 4.1. Экран входа

- По центру карточка: заголовок «Вход для мастера», поле пароля
  (`type="password"`, показ/скрытие по кнопке-глазу), кнопка «Войти».
- Ошибка неверного пароля — красным под полем, без подсказки «а какой надо».
- После трёх неудач подряд — пауза 30 секунд на клиенте (от случайного подбора
  простым перебором вручную; от настоящего брутфорса это не защита, см. раздел 7).
- Тема оформления и шрифты — те же, что на сайте; страница должна выглядеть
  частью проекта, а не чужой админкой.

### 4.2. Шапка кабинета

- Название и три счётчика: всего заказов, новых, сумма оплаченных.
- Кнопки: «Обновить» (повторный вызов функции), «Выйти».
- Строка «данные на …» с временем последнего обновления.

### 4.3. Фильтры и поиск

- Чипы статусов из справочника `order_statuses` (Новый, Подтверждён, …)
  со счётчиками по каждому.
- Поиск по номеру заказа, имени и телефону — фильтрация уже загруженного
  списка на клиенте, без новых запросов.
- Переключатель «показать только новые».

### 4.4. Список заказов

На широком экране — таблица, на мобильном — карточки:

| Колонка | Источник |
|---|---|
| № и дата | `orders.id`, `orders.created_at` |
| Статус | `order_statuses.name`, цвет по коду статуса |
| Клиент | `customer_name` + телефон |
| Позиций / сумма | количество `items`, `total + delivery_cost` |
| Оплата / доставка | `payment_methods.name`, `delivery_methods.name` |

Строка раскрывается по клику.

### 4.5. Раскрытый заказ

- Позиции: миниатюра фото, название, артикул, количество, цена, сумма строки.
- Контакты клиента: телефон и e-mail как кликабельные ссылки (`tel:`, `mailto:`),
  профиль ВК — ссылкой.
- Доставка: способ, пункт, стоимость.
- История статусов: список «статус — когда — кто изменил».
- Комментарий клиента.

### 4.6. Состояния, которые нужно предусмотреть

- Загрузка (скелетон или спиннер).
- «Заказов пока нет».
- «Пароль не подошёл».
- «Не удалось получить данные» + кнопка повторить (база недоступна).
- «Сессия устарела» — если хеш в sessionStorage очистили.

---

## 5. Хранение сессии на странице

- После успешного входа хеш пароля кладётся в `sessionStorage`
  (не в `localStorage` — закрываете вкладку, сессия заканчивается).
- При открытии страницы: если хеш есть, сразу пробуем `admin_orders`;
  не подошёл — показываем экран входа.
- Кнопка «Выйти» очищает `sessionStorage`.
- Сам пароль в sessionStorage **не пишется**, только хеш.

## 6. Этапы работ, когда дадите команду

| Этап | Содержание | Проверка |
|---|---|---|
| 1 | SQL-скрипт 06: таблица `admin_credentials`, три функции, RLS | тесты на PostgreSQL: неверный хеш не отдаёт данные, верный отдаёт, прямой `select orders` закрыт |
| 2 | `orders.html`: экран входа, список, раскрытие, фильтры | jsdom-тесты с подменой функции |
| 3 | Сквозной тест: страница против настоящей базы с тестовым паролем | e2e |
| 4 | Смена тестового пароля на ваш настоящий через `admin_set_password` | вручную в SQL Editor |
| 5 | Документация: раздел в техпаспорте и в `supabase/README.md` | — |

Ориентировочно это следующий большой шаг после фотографий товаров.

## 7. Чего в этой защите НЕТ (честно)

| Чего нет | Последствие | Что добавило бы |
|---|---|---|
| Серверной сессии и токенов | Хеш живёт в sessionStorage; у кого есть доступ к вкладке, видит данные до закрытия | Supabase Auth + JWT |
| Ограничения частоты на сервере | Подбор пароля перебором теоретически возможен | rate limit в функции или на уровне Edge Function |
| Журнала входов | Не видно, кто и когда заходил | таблица `admin_login_log` |
| Разделения ролей | Один пароль на всех | таблица пользователей и роли |
| HTTPS-_only cookie | — | настоящая аутентификация |

Для учебного проекта и личного использования этого достаточно: данные видны
только тому, кто знает пароль, а для всего интернета база закрыта политиками RLS.
Для настоящего магазина этот раздел нужно переделать на Supabase Auth.

## 8. Вопросы, которые стоит решить до реализации

1. **Пароль.** Придумайте и сообщите его способом, которому доверяете
   (или сгенерируйте сами и вставьте через `admin_set_password` — тогда
   он не появится ни в чате, ни в файлах).
2. **Нужен ли доступ с телефона.** Интерфейс планируется адаптивным,
   но на маленьком экране таблица превращается в карточки — проверьте, удобно ли.
3. **Показывать ли телефоны клиентов полностью.** Сейчас план показывает их
   как есть. Можно маскировать середину (`+7 925 ***-**-27`), если страница
   когда-нибудь будет открываться при посторонних.
4. **Нужна ли выгрузка в CSV.** Кнопка «скачать список заказов» делается
   за один вечер и полезна для сверки с оплатой.
